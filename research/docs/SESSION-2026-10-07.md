## The movement frontier (the one thing still open)

The client broadcasts its local-player state on **channel 1** (type `0x635`)
continuously and the server answers **only** on channel 0 and channel 3:

| Direction | ch0 | ch1 | ch3 |
| --- | --- | --- | --- |
| client -> server | 867 | **15688** | 16675 |
| server -> client | 1149 (+1892 ACK) | **0** | 16566 |

The capture has no 1:1 server reply to `0x635`. Two attempts to synthesise one
both failed and are recorded as negative results:

- re-sending `0x1096`/`0x1097` (they ride channel 0) - fixes the cable, not movement;
- echoing the client's own channel-1 body back on channel 1 - does not move the
  player and re-introduces the timeouts.

**Major lead found (2026-10-08).** The client ships a complete named movement
message family with AZ GUIDs: `StartMovementCommunicationMsg`,
`ReceivePlayerPositionClientMsg`, `AckMovementMsg`, `CommitMovementMsg`,
`CheckMovementStatusMsg`, `CancelMovementMsg`, `AbortMovementMsg`,
`MovementTimeoutMsg`, `ProcessDeferredMovementRequestsMsg`, `MoveActorMsg`,
`MoveActorToHubMsg`, `MoveAnActorMsg`. The full 156-type registry is in
[JAVELIN-MESSAGE-GUIDS.md](JAVELIN-MESSAGE-GUIDS.md). The client already has the
handlers; the server must drive this family, and the field layouts come from
decompiling those handlers. This replaces "a reply on channel 1/2" with a
concrete, named target list.

Separately, the gate-7 mechanism is now explained rather than empirical: the
typed dispatcher compares each inbound type GUID against a singleton set, and a
hit does **not** refresh the InGame activity clock while a miss does. `PingMsg`
is a singleton, which is why the `0x15d` heartbeat never cleared the timeout and
`0x1096`/`0x1097` did.
